## 2. SOLO 开源策略：合并 SoloMind 还是独立新 repo？

> （本轮发生于 #1 之后，收工时补录）· Claude Sonnet 4.6

**问：** 现在的 SOLO（同级目录 solo 里），如果后面开源的话，是合并到现在的 SoloMind，还是独立一个 git 来处理？

**答：** 建议开新 repo，不合并进 SoloMind。三条核心理由：
1. **git 历史清不干净**：solo 有 67 个 commit，含 `deploy/`、`vpn/`、`docs/security.md` 等私有文件，commit message 里也有内部基础设施细节；git filter-repo 能删文件但删不干净历史语义，风险留着。
2. **量级根本不同**：SoloMind 是「早期能跑的版本」，SOLO 是完整 AI-Native 中台（编排引擎、Event Bus、Permit 系统、ERP 适配层）；合并会让叙事乱。
3. **对外叙事更清晰**：SoloMind 留作「早期公开证据」，SOLO 新 repo 上线时写「SoloMind 是第一次验证，SOLO 是完整实现」——两个 repo 互相引用，反而更有说服力。
额外提示：若开源，建议只开 `core/` 层（orchestrator + agent + library），业务层保留私有；ERP 适配（用友 T+）需抽象为通用接口再放。

## 3. 小红书长文策略 + 发布节奏文档

> 08:44 · Claude Sonnet 4.6

**问：** 发布节奏写在文档里了吗？发现小红书有长文，长短比例怎么处理？长文适合哪些题材？

**答：**
- 节奏已有，在 `内容规划.md` 的「发布节奏」节，但只有三行，长文完全没提。
- 长短比例：短图文（150-300字）~70% / 长文（800字+）~30%；起号期可更激进偏短（80/20），有基础粉丝后再提长文比例；长文 1-2 周一篇即可。
- 适合长文的题材：方法论/思路类（D/B线）、宣言/定义类（元主线，如「AI后」定义文）、踩坑/复盘类（任意线）、设定集发布类（A线）；不适合：产品介绍、互动征集。
- 补进 `内容规划.md`「发布节奏」节。
